# Course and Reader: Codex review (security and design), 2026-11-22

Independent read-only review of commit 2405a59, kept verbatim.

## 1. Security review

**Block merge on the image decode limit.** Opening a public course can trigger a full-size browser decode before Flutter applies the requested display size. I found no confirmed script execution, dangerous-scheme launch, cross-repository read, or automatic remote image request. This was a read-only source review. I checked the Markdown and URI cases with the installed Dart SDK and did not run the Flutter suite or a browser build.

### High

- **Oversized images reach the decoder automatically.** A valid 12,000 × 12,000 PNG used as a cover or referenced by `![Figure](figure.png)` can reach the web decoder as soon as the page opens. One RGBA frame at that size takes about 550 MiB. `SizedImage` reads dimensions without enforcing a ceiling, and `CourseCover` sends bytes straight to `Image.memory`. Flutter 3.50.1 decodes an intrinsic-size frame to answer the resize callback. The test checks `ResizeImage.width`, which proves the requested size only. Enforce source width, height and total pixels before any decode on all three image entry points. Test rejection before codec invocation and verify display-sized variants in the actual web build. ### Medium

- **Encoded image bytes and the root README have no client size budget.** A 50 MB photograph can be buffered in full before any image check, and a 50 MB `README.md` can be joined into a string and passed to the Markdown parser on open. Both image loaders omit `maxBytes`. The root README uses the generated client’s unbounded `.join()`, while lesson Markdown already has a 512 KiB limit. Bound the response while reading, including when `Content-Length` is absent, and test that the rest of the screen stays usable after rejection. ### Low

- **Malformed and normalized paths defeat the intended refusal behavior.** `[Figure](%FF.png)` reaches the classifier intact and throws `FormatException` during percent-decoding. The helper catches only `ArgumentError`. For `![Figure](/%2e%2e/figure.png)`, the image builder receives a parsed `Uri` that has already normalized the path to `/figure.png`. The resulting read stays pinned, but the attempted climb is silently accepted. Classify the original image destination and test both inputs through the widget, asserting a fallback and zero reads. ## 2. Design changes, ranked

1. **Close the desktop gap.** At 1440, Contents ends at x308 and the text starts at x586. The 278 px gap makes the outline feel detached from the lesson it controls. Change the desktop placement rule to center the pane and reading column as one group, with a 64–80 dp gutter and the existing 576 dp prose measure.
2. **Give the course title the first read.** The 160 × 240 placeholder pushes the title to about y400 and the overview to y745. A second Lectale mark adds little there. Collapse the slot when there is no cover. When a course supplies one, try a smaller portrait beside the title and lead at desktop widths. The phone’s title-first order is the stronger hierarchy.
3. **Make Contents look operable.** On desktop it reads like a pane heading. On the phone it reads like a label next to a floating ribbon and status text. Add a graphite chevron to the control, put the ribbon at its leading edge when collapsed, and visually group the current place with it. Keep the 44 dp target and bring the first content heading about 12 dp closer on the phone.
4. **Make “In this lesson” scan like a file list.** The selected bar spans 576 px while both fields sit at the left, and the available row looks like passive copy. Align type and size at the row’s far edge when space allows. On phones, retain the second line and let the title wrap. Add a visible hover treatment and keep Sand plus semibold for selection.
5. **Remove the duplicate opening title on Course.** “Introduction to Statistics” appears twice before the first real paragraph at both widths. Suppress the visual repetition when the README’s first heading exactly matches the course title, preserving its anchor and leaving author-supplied headings intact in other cases.
6. **Make the PDF card a compact file handoff.** The 207 px panel looks like a stock alert. Give `testing.pdf` more weight, join type and size as one metadata line, shorten the explanation, and put the outline action alongside the file details on desktop. Stack it on phones. Also match the label to the behavior. The current action opens the URL, which a browser can display inline for PDFs. 7. **Bring the reader utilities together.** “Download” leads the filename, then “Python” and “Copy” float on a separate line above the code. Put filename and kind first and align Download at the trailing edge of that row. Bring Python and Copy into a slim header attached to the code surface. On narrow screens, wrap the file details as a unit.
8. **Make the lesson footer consistent.** The code page ends in a full-width gold banner and a centered Previous link. The PDF page uses a compact, two-ended footer. Use the latter alignment on desktop when the measured labels fit, and allow long titles to wrap within their controls. Keep the forward action first in the stacked phone layout.
9. **Improve the small UI type and keep the prose measure.** The 18/30 serif is comfortable in both the 576 px desktop column and the 354 px phone column. The module line, file kind and course facts are harder to scan. Bring instructional metadata to a consistent 14/20 Plex Sans where needed, and strengthen the module label slightly. There’s no need to shrink the reading text to recover space.
10. **Finish the sample figure.** The lesson describes a histogram and immediately shows an upward series of dots. That undercuts the teaching example, and the same pale slab dominates the dark screenshot. Use a real histogram with labeled axes in the demo course, and give that owned asset a dark variant with subdued contrast. Preserve the colors of figures supplied by course authors.

### Keep

- The warm paper, graphite and mulberry palette. The dark version carries the same identity.
- Source Serif 4 for reading, IBM Plex Sans for controls, and Plex Mono for filenames and code.
- The single swallowtail ribbon and the restrained gold primary action.
- One Contents hierarchy shared across Course and Reader, with Overview in a stable position.
- Readable code with line numbers, and a plain-language fallback when a file cannot be previewed.
